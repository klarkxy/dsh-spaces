## 1. 目标与已定边界

用户自行决定是否信任第三方插件。Spaces 负责记录安装与启动结果，并把失败、退出、崩溃的错误展示到对应空间和（能确定时）对应插件。不自动回滚安装环境，不把崩溃的空间重新拉起，也不提供手动恢复向导、Doctor 恢复或失败任务续跑。

### 保留

- 全局插件库负责发现、下载和复用制品；真正安装、配置与运行属于具体 Space。
- 新空间模板只影响以后创建的空间；已有空间不自动继承变化。模板导致运行失败就报错，不自动换模板、换依赖或改已有空间。
- 插件包依赖由官方 CLI 所用的包管理器处理，运行依赖由 Cordis 处理。
- Spaces 保护自己的管理组件与隔离配置，提示已知不兼容组合；未知组合允许尝试，失败只报错。
- 分享包、同机克隆和整 Home 是不同操作。导出是空间组成分享，不是整 Home 灾难恢复。整 Home 快照恢复作为产品能力已撤销。
- 安装/启动/崩溃错误必须可见，且尽量落到具体插件，而不是只显示空间挂了。不能附带修复建议或恢复入口。

### 不做（已撤销，不是延期）

- 普通插件安装/卸载的自动回滚、安装前恢复点、失败后撤销、重启后对账恢复、doctor 插件恢复入口。
- 整 Home 快照恢复、配置恢复、失败回滚、依赖环境拷回、journal 对账恢复。
- 失败项重试、原批次继续、中断续接、把旧失败改写成成功。
- 通用「已安装但停用」的运行控制协议；现有入口若实际是卸载，文案说卸载。用户看完错误后自行卸载或不管。
- 插件权限沙箱、代码审计、发布者签名体系、分级信任平台。
- 通用 capability 求解、自动选择 provider、自动编译 replaces、穷尽动态冲突。
- 后台自动改回用户通过 CLI 修改的配置；启动时自动升级第三方插件。
- 跨空间全成功或全撤销事务。
- V1 导入覆盖/合并已有空间，或导入到 `web`、管理空间。
- V1 离线分享包、跨机器原样复制 `node_modules`、复制正在运行的进程状态。

基础包格式检查、解压目录限制、Host 管理入口保护继续保留。这些用于保证操作对象正确，不扩展成第三方插件安全承诺。

## 2. 错误反馈承诺

全项目一致。详见 [docs/let-it-crash.md](../../docs/let-it-crash.md)。

| 对象 | 处理 |
|---|---|
| 安装/卸载 CLI 失败、中断、读回失败 | 留下任务错误；写明空间、包名、请求版本、阶段和原始输出摘要。不回滚磁盘，不换 latest |
| 空间启动失败、进程崩溃、非零退出 | 空间保持停止/崩溃。错误挂到该空间；能从 dump/日志/插件名对齐时再挂到具体插件 |
| 插件运行时报错但进程仍在 | 展示错误，不自动卸载、不自动重启，不人为杀掉宿主 |
| 目标空间 sessions/storages、其他空间、凭据、运行时 | 不因报错而改动 |
| 用户下一步 | 已有卸载/停止/启动入口是独立操作。报错本身不是修复，不附修复建议 |

不能确定是哪个插件时，允许只报到空间，并写明「未能归属到单个插件」，不得猜一个包名。

管理插件自升级是独立的用户主动维护，不混入普通插件安装错误，失败后不自动回退。

## 4. 最小实现约定

### 4.1 插件列表与下载

- 区分「插件库中的制品」「Profile 声明的包」「已配置的 bundle」；普通依赖不再伪装成可启用插件。
- `requestedSpec` 与实际 `resolvedVersion` 分开；未能读出实际版本就显示未知。
- UI 使用「已配置」与「空间启动检查结果」，不通过包名猜测所有运行实例均已正常。
- 现有“开关”实际执行安装/卸载的入口改成准确文案。不新增保留安装但停用的协议。
- 支持同一包多个版本并存，缓存记录来源、版本和内容摘要。
- 继续支持已有手动来源。无法固定版本/制品的来源显示相应信息，不静默换成 latest。
- 已知冲突采用少量明确规则；只有同一实际作用域内的重名才可能构成冲突。

### 4.2 安装与错误

复用现有写控制者、维护互斥和持久任务，执行：

`预览目标 → 停止受影响进程（若在跑）→ 写入操作记录 → 安装/卸载 → 读回 → 成功或留下错误`

- 不在修改前做安装环境恢复点，失败不自动拷回 `profiles/<space>/` 或 pnpm store。
- 记录任务 ID、目标、阶段、CLI/进程退出和检查结果。以真实输出为准，不把「已安装」显示成「已运行」。
- 安装失败、启动失败、进程崩溃：保持失败现场，展示错误。不要为了验收而把空间重新启动成看起来正常。
- 中断后下次打开仍显示未完成任务和最后错误；标明结果可能不确定。不重放、不对账、不补偿。
- 卸载仍走官方 `dsh plugin remove`。卸载失败同样只报错。

### 4.3 导入导出 V1

使用 `.dshspace` ZIP，格式尽量小：

```text
manifest.json       # 格式版本、来源环境、空间显示信息
plugins.json        # 插件来源、请求、实际版本、bundle 顺序
profile.patch.yml   # 可选的用户配置；只去除 Spaces 拥有的字段
assets/icon.png     # 可选
```

- V1 是在线重建空间的分享包，不保证不同机器得到完全相同的传递依赖树，也不是整 Home 灾难恢复。
- 默认导出插件组成、顺序和显示信息。用户可选择附带配置；导出前提供配置内容预览。
- 不导出 Home 配置、共享凭据、聊天、存储和 node_modules。Host 组件不作为用户插件导出。
- V1 在线自动安装支持可解析的 npm 来源；Git、本机目录等已有来源列为待手动安装。不得静默丢弃。
- 导入只创建新的普通空间。临时空间显式标为未发布，并从普通扫描、启动和批量选择中排除。
- **三个结果必须分开，不能混成一个状态：**

```text
空间定义：已导入
插件安装：已完成
空间启动：失败
错误原因：……
```

- 格式、路径和对象校验通过后可发布新空间定义。不能要求所有自由组合启动成功才允许空间存在。后续启动失败显示崩溃，不撤销已发布空间。
- 不能为了把导入验收做绿，偷偷调整依赖、禁用插件或换成能运行的组合。
- 导入失败时，只允许清理**本次能证明归属、尚未发布的临时资源**。不能回滚已经发布的空间，不能删除原有空间，也不建立跨重启的清理与恢复服务。宁可保留临时残留并报错。
- 不支持项目不兼容的新格式时给出说明；读取包内配置不执行其中表达式。

### 4.4 批量与模板

批量统一为：

```text
A：成功，保留结果
B：失败，记录错误
C：未执行
整批任务：失败终止
```

- 首项失败后结束该批次。删除失败项重试、原任务继续和中断续接。
- 用户以后主动选择其他目标再操作，是一份新请求。旧任务不续命，旧失败不因新操作成功而被改成成功。
- 共用下载结果，但不共用插件运行实例；不能重复执行已经成功的项目。
- 取消只跳过尚未开始项，不撤销已经发生的副作用。
- 新空间模板复用导入/创建流程，是创建时的副本。修改模板不更新现有空间。模板导致运行失败正常报错，不自动换模板或依赖。
- 同机克隆不纳入 V1 完成门槛。

## 6. 验收方法与实施纪律

- 不把历史 rc.1/rc.2 验收记录当成新功能通过。不把任务 01 的离线拷回实验当成产品已提供恢复。
- 单元测试针对版本解析、状态读回、错误归属（有插件名 / 无法归属）。集成验证使用一次性 Home、两个空间、可控失败插件。
- 故障展示至少覆盖：安装失败、启动失败、进程崩溃、安装中退出、合法但不兼容组合、批量 A/B/C。每项记录是否把错误展示给用户；并观察没有额外 spawn、安装、恢复调用、版本指针改写、清锁或配置补偿。
- 不能笼统要求“失败后整个 Home 完全不变”。原操作可能已经写入一部分，错误记录也可能落盘。应验证的是：没有在原操作失败之后额外发起恢复性修改。
- 测试插件只制造可控安装或启动故障；不用真实用户数据做故障注入。
- 复用现有诊断卡片、任务结果和 `lastError`；缺的是插件归属和「已配置 ≠ 已运行」，不是再做一套恢复框架。
- 每个里程碑补充本目录验收记录，更新任务清单。
- 不提交、推送或发布，除非用户届时明确要求。本次 D 阶段只改文档与任务；不宣称远端已更新。
