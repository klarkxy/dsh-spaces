# 发布前修复与独立验收（2026-09-11）

接续 [当前代码评审](review-2026-09-11.md)。Grok 负责后端修复初稿，Kimi 负责前端恢复流程；以下结论由 Codex 检查实际差异并独立执行测试获得。最终代码版本为 0.2.0，本机验收已完成；发布状态见 GitHub Releases。

## 修复内容

- 恢复操作的重试、数据替换、运行时选择、pending 清理及设置应用统一处理。无法完成恢复时继续阻止启动和写操作；重试不会把另一份待完成快照误报为本次请求成功。
- 当前运行时损坏时仍可进入版本恢复页。覆盖数据和仅备份数据分别确认；恢复前保留当前数据，缺少运行时的备份明确标记且不能作为完整恢复目标。
- 恢复完成同步设置表单，随后保存不会写回旧端口、软件源、语言或主题；恢复后保持空间停止，等待用户启动。
- macOS 打包同时生成 DMG 和自动更新所需 ZIP。没有将此配置检查描述为 macOS 安装实测。
- 实机测试追加修复：旧托管 Node 22.16 不支持新版 DSH 的 `import.meta.main`，现按能力升级并保留旧目录；可用的旧版快照不会因此强制联网升级 Node。
- 兼容 DSH 新版的本地浏览器认证、`session/list` 请求格式，以及旧版 `session.list`。只在旧接口返回 404 时尝试新版格式；认证失败不会被忽略。启动令牌保留在主进程，状态接口不返回令牌，日志脱敏。
- 选择仍在启动中的空间必须等待启动与认证完成，避免提前打开未认证页面。Windows 目录重命名遇到短暂占用只做 500ms 内的有限重试，超时仍报错。
- 旧版 DSH 首次并发启动会竞争生成共享依赖链接。ProcessManager 在各空间并发校验/启动前只初始化一次，失败可重试，全停维护后重新初始化。

- 使用隔离工具目录，真实从旧托管 Node 迁移至 22.23.2；旧安装保留，新 Node 支持 CLI 入口。未写入用户原工具目录。

- 真正的 0.1.1-rc.2 → 0.1.5-rc.1 协调升级通过阶段检查及提交，三个空间原会话保留、互不可见，patch 字节未改变，用户显式启动正常。回退已替换数据并选择旧快照运行时，同时保存新版数据备份。原脚本此时发现首次并发启动竞态；修复后在同一个已回退环境连续三次清除可再生依赖链接、并发启动三个空间，确认原会话完整且隔离，端口全停。该闭环为分段验证，复测脚本为 `restored-upgrade-check.mjs`，未把首次失败写成一次性全流程通过。
- `v0.2.0` Windows 解包程序：新版 web/coding/writing 页面加载，嵌入页面通过浏览器认证调用会话接口；退出后全部测试端口关闭。
- `v0.2.0` Windows 解包程序：损坏当前运行时后进入恢复页，未确认时拒绝恢复；双确认后恢复完整旧快照，新增数据保存在仅数据备份，身份标记保留。保存表单保持恢复后的设置；手动启动可读原会话并加载旧版离线页面，退出关闭端口。

## 验收脚本与限制

最终 NSIS 包实际静默安装到项目隔离目录后，使用安装目录中的程序再次通过新版三空间页面/认证接口，以及损坏运行时恢复/设置保存/原会话/旧版页面可见/退出端口清理检查。主进程检查嵌入视图可见且有有效尺寸，直接捕获其页面检查。验收副本已卸载，系统安装项已清理。安装向导逐页点击未测试；这是实际安装后程序验收，不是把解包启动冒充安装。

最后验收包：`.sandbox/release-0.2.0-final/DSH Spaces Setup 0.2.0.exe`，SHA-256 `B86ECC2F123446C1DDBA8BE60F4D603FAF136E511EE35918B6B13E0A3294CAA8`。CI 发布包由同一版本代码重新构建，不能把本地哈希当作 CI 产物哈希。两处既有单元测试补齐初始化替身，最终 179 项全量测试已确认不再生成真实 CLI 配置夹具。

可重复脚本：`real-runtime-install.mjs`、`real-upgrade-check.mjs`、`restored-upgrade-check.mjs`、`candidate-ui-check.mjs`、`recovery-acceptance.mjs`。全部使用临时 Home 和临时应用目录，不调用模型、不读取用户真实聊天。
