# Supervisor component handoff wiring

Primary fixed wiring for the existing B5 design; no additional daemon or recovery path.

- Add Node-only `componentPayloadRoot` (`--component-payload`) and `acceptHandoff` (`--accept-handoff`, boolean) CLI options. The entry is from the selected manifest and the worker/LLM/view resources must be from that same validated group. Ordinary public browser commands never accept paths or ownership tokens.
- Add internal-only accepted `HomeControlHandle` input and a CLI-only normal-exit callback. `--accept-handoff` begins IPC before runtime construction, receives its token, accepts the Home run reservation with the preserved explicit nonzero `--port` endpoint, and only then creates the Supervisor. Runtime verifies the handle still agrees with the current owner and its actual HTTP origin, uses it instead of acquire, and creates a fresh epoch/bearer. No Node client fallback acquires on failure.
- CLI reports final IPC success only after runtime initialization, HTTP and the manager are ready. Use the lower-level `beginAcceptHandoffChild` so lock acceptance is not mistaken for completed startup. A later startup failure reports failure and exits without releasing the accepted run owner or reverting selection. No auto-retry.
- Construct WorkbenchPackageUpgrade with `toolsRoot` and the new handoff callback only when the running CLI can exit normally and owns a validated component payload. A library-created Supervisor without that capability rejects upgrade before stop or install. Package usecase supplies `{planId,snapshotId,payload}`; it has already stopped owned spaces, created backup, installed and verified candidate bytes. The callback confirms no owned child is still running, seals further mutations, saves a pending handoff in memory, and sets job phase/message to handoff-pending (preparation complete, new service startup unconfirmed). It does not wait for its own job tail.
- At the existing plan.execute `whenIdle` continuation, if and only if that exact job succeeded, finalize the pending handoff. A failed final job persist must never trigger transfer. Close old HTTP/endpoint while retaining the run owner. Spawn the one-shot launcher from the old validated component group. Transfer the same run directory to that live launcher using binding for canonical Home/old epoch/new payload digest. Send and await the IPC commit flush with explicit clean-stop confirmation. New runtime argv carries exact selected entry/payload/worker, preserved Home/runtime/snapshot/tools and nonzero port; pack plugin/view/LLM from the staged selected group before stopping where needed. Exit old CLI normally, with no release of transferred owner.
- Failure before transfer keeps old owner and old pointer plus a bounded public diagnostic. Failure after transfer keeps the reservation and pointer evidence. The launcher confirms old process death before switching; no replacement service is started by the old Supervisor. A second close or plan cannot release the handoff owner.
- The old job's terminal result means handoff preparation, not confirmed new service startup. Its phase remains handoff-pending; final result is the bounded launcher receipt. Do not report completed update in the old UI merely because this preparation job succeeded.

Use real subprocess coverage for the CLI accept boundary and Supervisor integration where practical. At minimum prove no-callback preflight refusal, transfer only after durable job settlement/clean stop, no transfer on failed stop or final job write, preserved epoch rejection, and no acquire before token acceptance. Existing HomeController/launcher process tests cover the primitive contention windows; do not replace them with mock-only checks.
